# Implementation notes

- The application uses the Rails API stack with Active Record and PostgreSQL. Mail, browser assets, file storage, Action Cable, Active Job, and deployment scaffolding are omitted. Later delivery work will use database rows as its durable work source.
- Development and test use explicitly configured, separate database URLs. Test-environment boot rejects a database name matching development or production before schema preparation. Minitest runs in one process to keep local resource use bounded.
- All six domain records use PostgreSQL-generated UUIDs. Unique indexes protect tenant/event idempotency keys, event/endpoint delivery pairs, credential digests, and delivery/run/attempt identities. Endpoint URLs are intentionally not unique: separate registrations represent separate destinations.
- Deliveries reference both events and endpoints through composite foreign keys containing `tenant_id`. A valid resource UUID cannot be linked to a delivery belonging to another tenant. Associations alone do not provide API authorization.
- Events retain parsed JSON data and the exact outbound bytes supplied at creation. Persisted events are read-only in Rails; a PostgreSQL trigger rejects updates and deletes, including bulk writes. The original fan-out count is immutable. The SQL schema format preserves the trigger when rebuilding a database, as described in the [Rails migration guide](https://guides.rubyonrails.org/v8.1/active_record_migrations.html#using-the-sql-schema-dumper).
- Internal event ingestion requires a case-sensitive 1–128 character ASCII idempotency key containing only letters, digits, `.`, `_`, `:`, or `-`. It validates before key lookup and fingerprints the exact UTF-8 request bytes with SHA-256. Matching retries return the original event and stored outbound body; changed valid bytes conflict, including whitespace or field-order changes. Keys are tenant-scoped and have no automatic expiry. Validation failures and rolled-back transactions do not reserve keys.
- Ingestion serializes on the tenant row before checking the unique `(tenant_id, idempotency_key)` identity. Competing requests therefore observe the committed winner under PostgreSQL's default read-committed isolation; the database index independently prevents duplicate identities. The event UUID, microsecond timestamp, and outbound JSON envelope are generated once for a new event. Data must be an object; NUL characters in keys/strings and non-finite numbers are rejected before persistence because PostgreSQL JSONB cannot store them. The public ingestion route remains closed until the same transaction creates the endpoint snapshot and delivery rows; the internal service currently creates events with zero deliveries.
- Check constraints bound attempt numbers to 1–8, require positive run numbers, constrain states and outcomes, and keep schedules and completion timestamps consistent with row state. A partial unique index permits at most one in-progress attempt per delivery across runs. Cross-row counter updates, legal state transitions, leases, and replay serialization still require transactional services.
- API credentials contain 32 cryptographically random bytes encoded as unpadded base64url with a `whapi_` prefix. Only SHA-256 digests are persisted. High-entropy generated credentials permit indexed digest lookup; they are not user-chosen passwords. Issuance returns the raw credential only to the caller, and the local command prints it after commit. Revocation retains the first committed revocation timestamp and prevents later authentication without invalidating other credentials.
- `V1::BaseController` authenticates before actions and keeps the tenant on the controller instance, avoiding shared request identity. Scoped lookup helpers use the tenant's associations; nested lookups must continue from an already-scoped parent, and creation must use tenant associations rather than client ownership fields. This is an application boundary, not PostgreSQL row-level security: direct database access remains trusted. Every future resource controller must use these scopes. Credential, authorization, and secret parameter names are filtered; raw credentials and signing secrets are never passed to SQL or explicitly logged.
- Endpoint signing secrets contain 32 random bytes encoded as unpadded base64url with a `whsec_` prefix. `ActiveSupport::MessageEncryptor` encrypts them using AES-256-GCM and JSON serialization, binding the authenticated ciphertext to the endpoint UUID. A separate stable encryption key comes from an environment variable or an ignored, owner-readable local key file. The plaintext is available internally for future signing, but API representations explicitly select public fields; only creation adds the secret. Key rotation and recovery without the original key are outside scope.
- Registration permits HTTPS on port 443 and preserves the URL bytes. DNS has a three-second deadline; every returned address must pass the policy. The policy conservatively excludes IPv4 special-purpose blocks and permits IPv6 global unicast only, excluding special-purpose and transition ranges. It rejects IPv4-mapped IPv6 and special-purpose exceptions even when some are globally reachable. The range choices follow the [IANA IPv4](https://www.iana.org/assignments/iana-ipv4-special-registry) and [IPv6 registries](https://www.iana.org/assignments/iana-ipv6-special-registry). Registration validation is only an initial check: future outbound transport must revalidate DNS and pin the actual connection address, reject redirects, and enforce time and response-size limits.
- Endpoint lifecycle operations serialize with tenant, then endpoint, then delivery locks. Registration takes the tenant lock; disabling takes both parent locks and atomically cancels only queued deliveries, preserving the first disable timestamp. `EndpointLifecycle.with_active_endpoint` provides the same lock order and active-state check for future database-only work. Ingestion must lock the tenant before its endpoint snapshot, and claims/replay must use the active-state guard before changing delivery rows. No network I/O belongs inside these transactions. The tenant lock deliberately favors simple, provable ordering over per-tenant throughput.
- An earlier claim can outlive disable. Future workers must cancel before sending when they observe disable; otherwise they preserve the actual attempt outcome, record success on a successful response, and cancel without retry on any other outcome or lease expiry. Disabling leaves running rows and all completed history untouched. Database concurrency tests exercise the lifecycle guard in both lock orders; they do not establish worker behavior before workers exist.
- A middleware before Rails request logging reads at most 65,537 body bytes, enforces the 65,536-byte limit without trusting `Content-Length`, and rejects duplicate keys, invalid UTF-8, unsupported encodings, non-object roots, and excessive nesting. JSON parsing and media-type rules apply when a body is present; bodyless requests continue to authentication and field validation. Accepted parsed parameters are reused by Rails so its default parser cannot silently overwrite duplicate keys. Resource field validation runs after authentication. Endpoint lists use signed, tenant- and route-bound keyset cursors over `(created_at, id)`; list changes between pages are expected.
- Setup prepares both local databases without resetting them. Checks run with the test environment and include Rails' Zeitwerk autoload validation.
- The application exposes endpoint-management routes. The internal event-ingestion service has no public route or delivery fan-out yet. Outbound connection safety, retries, replay, and worker concurrency remain unimplemented.
- Version selection was checked against the official [Ruby maintenance branches](https://www.ruby-lang.org/en/downloads/branches/), [Rails releases](https://rubyonrails.org/releases), [Rails maintenance policy](https://rubyonrails.org/maintenance), and [PostgreSQL versioning policy](https://www.postgresql.org/support/versioning/). Rails 8.1 remains under security maintenance through October 10, 2027; its listed general bug-fix window has ended. Review supported patch releases before subsequent upgrades.
